PART 01 / 信创与可扩展

信创与可扩展

这一部分只回答两个问题：技术上有没有商业授权风险，以及业务涨上来之后扩容要付多大代价。三页 PPT，五个要点，讲完直接进自主可控。

5 分钟 形式：纯 PPT 关键词：TDengine · 分层扩容 · 3 万台
05信创选型：国产时序库 TDengine选型

时序数据落在国产库上，全栈不背商业许可费

信创不是换一个 Logo，而是把"授权"这条风险从架构里拿掉。

  • 时序库选用国产 TDengine，设备与测点数据按"一设备一子表"组织，天然贴合工业时序场景。 平台侧只负责产生规范化的遥测与事件消息，入湖由数据入湖服务完成，存储层与业务层解耦。
  • 全栈无商业许可费用，不引入按节点、按设备、按核数计费的商业授权组件。 扩容时增加的是服务器资源，而不是一份新的 License 合同——这条在五年、十年的周期里，差的是数量级。
  • 规避授权风险，包括许可到期、审计追溯、版本升级被许可条款反向约束这三类常见问题。 开源组件的运维责任由我方承担，私有镜像仓库保证版本可追溯、可回滚。
成本项商业时序库方案本方案（TDengine + 自研平台）
软件许可按节点 / 设备规模计费，随扩容递增无商业许可费
扩容边际成本算力 + 新增授权仅算力与运维人力

建议版式：左侧「TDengine」技术栈卡（国产·开源·时序专用），右侧成本对比表；不要放厂商 Logo 墙，客户更关心成本结构而不是品牌数量。

讲稿约 1 分 40 秒

第一页讲选型。时序数据是物联网平台里增长最快、也最容易把成本拖爆的部分。我们的选择是国产 TDengine，按"一设备一子表"来组织，这跟工业场景里"设备多、测点多、写入密集、查询按时间窗"的形态是对得上的。

更关键的是授权结构。这套栈里没有按节点、按设备、按核数计费的商业授权组件。这意味着什么？意味着贵方业务翻一倍，增加的是服务器，不是一份新的 License 合同。

我把话说得更直白一点：商业库的风险不在于贵，而在于它会在你最需要扩容的时候，变成一张必须谈的合同。开源方案把这件事变成了纯技术问题——加机器、加副本，运维责任由我方承担。

预判追问 如果问"开源库出问题谁兜底"：由我方兜底。我们持有内核源码、维护私有镜像仓库，出问题可以改代码、可以回滚版本，这是下一部分"自主可控"要展开的内容。

06微服务架构：按层独立水平扩容架构

接入、规则、脚本三层解耦，谁先到瓶颈就扩谁

扩容不是"整机加配"，而是"按层加副本"——这是架构决定的，不是运维技巧。

L1接入层

MQTT 接入与设备会话。设备数增长、连接数增长时优先横向扩这一层，多副本前置负载均衡。

L2规则引擎

按产品生成规则链，负责遥测校验、事件分流与消息外发。计算密集时独立扩，不牵连接入。

L3脚本引擎

规则链内的脚本与计算逻辑。复杂规则、批量加工时单独扩容，避免拖慢主链路。

# 数据主链路（与扩容单元一一对应）
设备 ──MQTT──▶ 接入层 ──▶ 产品配置 ──▶ 规则引擎 / 产品规则链 ──▶ 遥测存储
                                              │
                                              ├─▶ Kafka: iot.telemetry.normalized
                                              ├─▶ Kafka: iot.event.normalized
                                              └─▶ Kafka: iot.invalid（非法数据隔离）
                                                        │
                                                        ▼
                                              数据入湖服务 ──▶ TDengine（超级表 / 子表）

# 扩容动作
接入层副本 +N  ← 设备连接数上涨
规则引擎副本 +N ← 校验与转发吞吐上涨
脚本引擎副本 +N ← 复杂计算规则增多
# 以上均为水平扩容，不改业务代码、不改数据模型

建议版式：横向三泳道架构图，泳道下方标「扩容单元」箭头；把 Kafka 三条主题画出来，能直接支撑"非法数据不污染时序库"的说法。

讲稿约 1 分 50 秒

第二页是架构。很多平台说"支持扩容"，实际是整机加 CPU 内存，或者换一台更大的机器——那不叫可扩展，那叫加预算。

我们的接入层、规则引擎、脚本引擎是分层解耦的。设备连接数先到瓶颈，就扩接入层；校验和转发吞吐不够，就扩规则引擎；某个产品的脚本计算特别重，就单独扩脚本引擎。每一层都是无状态副本，前面挂负载均衡，加副本即可，不改架构、不改代码。

还有一条容易被忽略：非法数据是走独立主题隔离的，不写时序库。所以一条脏数据不会把存储层拖垮，也不会污染历史查询。

预判追问 如果客户看过部署文档，会问"为什么产品与物模型服务是单副本"。要正面回答：那是数据库迁移顺序的部署约束，不是架构限制；把迁移拆成独立 Job 之后就能多副本滚动升级。这个我们已经在设计里，不回避。

073 万台验证与扩容动作验证

单集群已验证 3 万台设备接入，扩容只加副本

这一页只讲结论：规模不是靠"规划"支撑的，是靠跑过的集群支撑的。

∞横向

3 万台设备 / 单集群已跑通接入、校验、存储全链路。数量继续上涨时，加节点、加副本，架构不变。

↺纵向

单副本资源按需上调，用于吸收突发流量；常态扩容仍以水平副本为主，避免单点规格成为天花板。

场景现象动作架构变更
设备数翻倍接入连接数与会话数上升接入层副本 +N，前置 LB 扩容无
上报频率提高规则链校验与转发吞吐吃紧规则引擎副本 +N无
规则复杂度上升脚本执行时间变长脚本引擎独立扩容无

建议版式：左侧一个「3 万」大数字 + 测试口径小字，右侧四行扩容动作表。数字要大，口径要小——这页的说服力来自"敢把条件写出来"。

讲稿约 1 分 30 秒

第三页给结论：单集群已经验证过 3 万台设备接入。接入、校验、存储整条链路都跑通了，不是只测了连接数。

更重要的是扩容动作。设备翻倍，扩接入层；上报频率上去，扩规则引擎；规则变复杂，扩脚本引擎；历史数据膨胀，TDengine 加节点、按时间分区。四种增长，四种加法，没有一种需要改架构。

这就是"可扩展"这三个字真正的含义——增长是可以被预算的，而不是要被重新设计的。

预判追问 问"3 万台的测试条件是什么"：详细压测报告可以会后提供，包含并发连接、上报频率、消息大小、集群规格。这一页讲的是结论和扩容路径，条件放在报告里，不藏在话术里。

PART 02 / 自主可控

自主可控

自主可控常被讲成一句口号。我们把它拆成三层可验证的事实：源码在谁手里、数据落在哪里、整套系统能不能搬走。三层都成立，才叫可控。

4 分钟 形式：纯 PPT 关键词：源码 · 自有库表 · 私有仓库 · TKE
08第一层：源码可控研发

内核源码全量可控，功能定制与版本迭代由我方直接发版

不需要向原厂提需求、等排期、等版本——这条决定了响应速度。

  • 内核源码全量可控，包括接入、规则链、物模型、前端在内的完整代码基线，不是只拿到二进制或扩展点。 客户提出的定制需求，走的是"改代码 + 发版"，不是"提工单 + 等原厂"。
  • 功能定制与版本迭代由我方直接发版，版本节奏跟随项目，而不是跟随上游社区日历。 私有镜像仓库保留每个版本的镜像与制品，升级可灰度、可回滚。
  • 依赖边界清晰，平台元数据用 PostgreSQL，时序数据用 TDengine，消息用 Kafka，均为可自主部署的开源组件。 没有"必须连回厂商云"的隐藏依赖，断网环境同样可交付。

1改得动

需求进来，能直接改内核，不依赖第三方排期。

2发得出

自有流水线与镜像仓库，版本由项目节奏决定。

3退得回

镜像与数据库迁移都可回滚，升级不是单向门。

建议版式：一条「需求 → 改码 → 构建 → 私有仓库 → 灰度 → 回滚」的横向流程条，三个卡片压在流程下方，强调闭环。

讲稿约 1 分 20 秒

自主可控第一层，源码。这句话很空，我把它翻译成三个动作：改得动、发得出、退得回。

改得动，是客户提的需求我们能直接改内核，不用写邮件等原厂排期。发得出，是我们有自己的流水线和私有镜像仓库，版本节奏跟项目走。退得回，是升级出问题能回滚镜像、能回滚数据迁移。

这三件事合起来，才叫"版本控制权在自己手里"。只给二开接口、不给源码的方案，第一件事就做不到。

预判追问 如果问"你们改的是社区版，上游升级怎么办"：我们维护自己的基线分支，上游安全补丁按需回合，不强制跟随上游大版本。这是自研平台的标准做法，不是临时方案。

设备、时序、物模型数据全部落在自有集群、自有库表

没有任何一类业务数据被托管到第三方，也没有"数据换服务"的结构。

第四部分，融合终端。现场的情况大家比我熟：一条产线上可能同时有 OPC-UA 的 PLC、西门子的 S7 设备、还有 CAN 总线的工程机械。协议不统一，是常态。

我们的做法是把协议收敛在一台边缘网关里：OPC-UA 按节点读、S7 直接读 DB 块、CAN 解析帧，全部在网关内部完成映射。对外，它只有一条 MQTT 连接。

这样平台侧看到的东西就很干净——一个网关设备，下面挂若干子设备，关系是标准的 Contains。平台不需要知道现场用的是哪种总线，这是解耦的关键。

网关 MQTT 客户端直连平台网关模式，平台原生支持网关主题与子设备关系。没有中转服务这一层。

这一页回答一个很具体的担心：是不是还要再加一台中转服务器？答案是不用。

传统方案里，网关连中转、中转再连平台，中间那一层要做协议转换、要做转发、还要单独监控和扩容。多一层，就多一个故障点，也多一套要维护的东西。

我们的融合网关，MQTT 客户端直接连平台的网关模式。平台原生支持网关主题、支持网关和子设备的包含关系。所以链路上没有中转服务这一段。

这对现场意味着什么？少一台机器、少一个要盯的服务、排障的时候少跨一个系统。

预判追问 如果问"网关坏了怎么办"：子设备数据在网关本地有缓存，换一台网关、恢复配置和凭证即可续传；这也是把复杂度放在边缘的代价，我们认这个代价。

17融合网关使用同一个标准物模型建模一致

网关与子设备共享一套物模型语言

不是"网关一套格式、平台一套格式"，而是同一份 TSL、同一套校验规则、同一条规则链。

  • 同一份 TSL：子设备的属性、事件、行为定义沿用产品物模型，网关只做点位到字段的映射。 同一个型号的设备，换一个网关接入，物模型不用重建。
  • 同一套校验：网关上报的遥测同样过产品规则链，类型、范围、枚举、必填一项不少。 不会因为"走了网关"就降低数据质量门槛。
  • 同一条链路：子设备数据与直连设备走同一个 Kafka 主题、同一套入湖逻辑。 下游不用区分"这是网关来的还是直连来的"。

↔横向：多网关复用

同一产品在多个工点、多台网关上复用同一份物模型，新增工点只加网关实例。

↕纵向：平台无感

平台侧不区分接入方式，规则、告警、看板、API 全部按统一模型工作。

建议版式：中间一份 TSL 文档图标，向上连网关、向下连平台规则链，左右各一个"复用 / 无感"说明；强调"一份模型"而不是"两套适配"。

讲稿约 1 分 20 秒

第三页讲建模。很多网关方案的问题是：网关一套数据格式，平台一套模型，中间要写适配，适配一多就没人维护得动。

我们的做法是同一份 TSL。子设备的属性、事件、行为，沿用产品的物模型定义；网关只负责把 OPC-UA 的节点、S7 的 DB 块、CAN 的帧，映射到模型字段上。

而且网关来的数据同样过产品规则链，类型、范围、枚举、必填，一项不少。不会因为走了网关就放松校验——这条很重要，否则数据质量会分层。

对下游来说更简单：子设备数据和直连设备走同一个主题、同一套入湖，平台不需要知道它是怎么接进来的。

19物模型按腾讯 TSL 规范归一化兼容

腾讯侧的物模型，可以直接导入

平台在导入入口就完成格式识别与归一化，客户不需要先"翻译"一遍。

  • 按腾讯 TSL 规范归一化：属性、事件、行为统一映射到平台标准 TSL，保留类型、范围、单位、枚举、结构体层级。 归一化发生在导入阶段，落库的是标准模型，后续规则链、看板、API 全部按标准模型工作。
  • 腾讯侧物模型可直接导入：不需要先导出成表格、再人工重建；导入即识别、即校验、即生效。 对存量项目，这一步省掉的是"重建模型 + 重新联调"的整段时间。
  • 识别是自动的：平台根据物模型特征（腾讯格式的 define 定义）判定来源，不要求操作员先声明"这是腾讯格式"。 标准 TSL 与腾讯格式走同一个导入入口，不会导错。

✓保留的信息

数据类型、取值范围、枚举映射、单位、读写模式、事件参数、结构体字段层级。

!需要确认的信息

字符串型 min/max 这类源数据元信息，默认按规范丢弃；需要保留时用参数显式开启，不偷偷改语义。

建议版式：左侧腾讯 TSL 片段、右侧平台 TSL 片段，中间一个大箭头标「归一化」；下方用两个卡片区分"保留"与"需确认"，体现严谨。

讲稿约 1 分 30 秒

最后一部分，腾讯云 IoT 兼容。这一段的背景很实际：贵方已有腾讯侧的平台和物模型，迁移最大的成本不是平台，是模型重建和设备重联调。

我们的做法是：在导入入口做归一化。腾讯的物模型进来，自动识别、自动映射到平台标准 TSL，类型、范围、枚举、结构体层级都保留。落库的是标准模型，后面规则链、看板、API 都按标准模型走。

有一个细节我想说明：识别是自动判断的，不要求操作员先声明"这是腾讯格式"，标准 TSL 和腾讯格式走同一个入口，不会导错。

另外，字符串型 min/max 这种源数据元信息，默认按规范丢弃；要保留就得显式开参数。我们不改语义，只做显式转换。

20内置腾讯格式转换器双向

双向转换，设备端协议与上报格式都不用动

迁移不是单向的"搬进来"，也包括将来"导回去"——所以转换器做成双向。

转换项腾讯 IoT 物模型平台标准 TSL
字段类型dataTypetype
数值范围字符串形式 "0" / "100"数值 0 / 100
枚举stringenum + mappingenum_string，mapping 保留
结构体struct.specs 数组以字段 id 为键的对象

# 腾讯侧（节选）

建议版式：上方字段映射表，下方左右两段 JSON 对比（腾讯 / 平台），高亮改动的那两行；不要贴整份 JSON，客户看的是规则不是全文。

讲稿约 1 分 40 秒

这一页讲转换器。为什么要强调"双向"？因为迁移不是单向的——今天搬进来，将来也可能要导回腾讯侧做对比或并行，所以两个方向都得有。

具体规则不复杂，但有三个坑：数值字符串要转数字、stringenum 要映射成 enum_string、struct 的 specs 数组要转成对象。这些如果靠人工改，量大了一定出错；做成转换器，规则固定、可回归测试。

对客户最重要的两句话在下面：迁移不改设备端协议，也不改上报格式。设备该发什么还发什么，字段名、类型、时间戳口径保持一致，历史数据和实时数据的语义是连续的。

A4Q&A 应答库高频 8 问

被追问时，先给结论，再给证据，最后给边界

问题建议应答（要点）
为什么不用大厂托管 IoT？托管方案省运维，但数据与授权受制于人；本方案可私有化、可迁移、无许可费。规模化后成本结构差异会放大。
TDengine 开源版够用吗？时序写入与聚合查询够用；若需要企业级支持，可另行采购服务，属于运维选项而非架构前提。
3 万台的测试条件？压测报告含并发连接、上报频率、报文大小与集群规格；本页讲结论，条件可会后提供。
AI 是否会把数据传到外部？模型服务地址可配置；敏感数据不进模型上下文，完整物模型走服务端 handler，不整包喂给模型。
AI 生成错了怎么办？生成物是草案，必须过平台结构与业务校验；写操作需人工确认；高危操作二次确认并审计。
迁移要多久？取决于物模型数量与设备协议；建议先做 2–3 个真实物模型的导入评估，再给整体排期。设备端不改是最大变量消除。
历史数据能迁吗？时序数据可按时间分区批量导入；建议历史归档 + 新数据双轨一段时间，验证后再切换。
出问题谁负责？源码、镜像、部署均在交付范围内，问题定位到代码级；运维责任边界在交付协议中明确。

!三条禁忌

不承诺未验证的容量数字；不承诺未排期的功能上线时间；不在客户面前评价友商产品，只对比方案结构。
