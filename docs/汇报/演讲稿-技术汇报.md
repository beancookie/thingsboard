# 第一部分　信创与可扩展

## 03 技术选型：国产时序库

*约 40 秒*

### 时序库选国产 TDengine，全栈无商业许可费

- **国产时序库**：TDengine 3 节点集群承担时序数据存储，一设备一子表，按产品建超级表；线上 45,738 张时序表
- **零许可费**：不按节点、设备、核数计费；扩容增加的是服务器，不是合同
- **规避三类授权风险**：许可到期、审计追溯、升级被条款反向约束
- **成本结构**：扩容边际成本 = 算力 + 运维，不含新增授权

| 成本项 | 商业时序库方案 | 本方案 |
| --- | --- | --- |
| 软件许可 | 随规模递增 | **无** |
| 扩容成本 | 算力 + 授权 | **仅算力** |
| 授权审计 | 长期台账 | **无此事项** |
| 版本升级 | 受商业周期约束 | **自主发版** |

## 04 架构：核心组件可灵活扩容

*约 40 秒*

### 平台网关、时序数仓、关系型数据库，三类核心组件各自灵活扩容

| 核心组件 | 承担什么 | 扩容方式 |
| --- | --- | --- |
| 平台网关 | 设备接入、协议解析、规则处理与消息转发 | 加实例 / 加副本，前置负载均衡 |
| 时序数仓 | 遥测与事件存储、按时间窗查询 | 加节点 / 加副本，按时间分区 |
| 关系型数据库 | 设备与凭证、产品与物模型、规则配置 | 加实例 / 读写分离，按需升配 |

**扩容原则**：哪一类先到瓶颈就扩哪一类，不改业务代码、不改数据模型。

**一句话**：接入、存储、配置分开扩，扩容只是加资源。

## 05 实测：3 万台设备接入

*约 40 秒*

### 单集群已验证 3 万台设备接入，扩容路径清晰

- **实测规模**：单集群 3 万台设备，接入、校验、存储全链路跑通
- **三类增长、三种加法**：接入压力 → 平台网关加实例；写入与历史数据 → 时序数仓加节点 / 分区；设备与产品数据增长 → 关系型数据库加实例
- **架构不变**：以上扩容均不需修改架构
- **口径**：压测条件见报告，本页只给结论

| 场景 | 动作 | 改架构 |
| --- | --- | --- |
| 接入压力上升 | 平台网关加实例 / 副本 | 否 |
| 时序数据膨胀 | 时序数仓加节点 / 时间分区 | 否 |
| 设备与产品数据增长 | 关系型数据库加实例 / 升配 | 否 |

# 第三部分　定位：不是产品，而是系统

## 12 我们的定位：不是卖产品，是交系统

*约 40 秒*

### 交付的不是一个固定产品，而是一套完全可控、可定制的系统

| 维度 | 标准化产品 | 我们交付的系统 |
| --- | --- | --- |
| 能力边界 | 厂商定义，需求要等版本 | 按业务定制，需求可排期 |
| 源码与数据 | 不开放或部分开放 | 全量源码、数据自有 |
| 对接方式 | 按产品接口适配 | 按现场协议与模型定制 |
| 演进节奏 | 跟随厂商路线图 | 跟随项目与业务节奏 |
| 退出成本 | 换产品等于重建 | 系统可迁移、可延续 |

- **更灵活**：协议、模型、流程都能按现场改，不被产品功能表限制
- **更高效**：不绕弯适配，直接改到业务需要的样子
- **更贴近业务**：以现场工点、设备、工况为准，而不是以产品功能为准

**一句话**：买产品是买一个盒子，交系统是交一套能跟着业务长的能力。

## 13 系统化交付的三个结果

*约 40 秒*

### 灵活、高效、贴近业务，不是形容词，是三个可验证的结果

| 关键词 | 具体表现 | 怎么验证 |
| --- | --- | --- |
| 更灵活 | 接口、协议、规则链、物模型均可定制 | 看定制过的规则链与接入协议清单 |
| 更高效 | 需求直接改代码，不排队等版本 | 看需求到发版的周期记录 |
| 更贴近业务 | 模型与流程按工点、设备、工况设计 | 看物模型与现场台账的对应关系 |

- **不是"什么都能做"**：范围以合同与需求清单为准，不做无边界的承诺
- **也不是"什么都要改"**：标准能力开箱即用，定制只发生在真正需要的地方
- **交付物**：源码、镜像、部署清单、接入规范、运维手册

**一句话**：可控是前提，可定制是手段，贴近业务才是目的。

# 第四部分　AI 辅助

## 14 AI 辅助总览

*约 40 秒*

### 从建模型、改模型到调接口、写代码，一条原则：AI 只提建议，平台校验执行

| 场景 | 能力 | 交付价值 |
| --- | --- | --- |
| A 物模型 | 导入物模型，AI 校验并生成产品 | 缩短新产品上线周期 |

- **全量覆盖**：平台所有 REST API 都已接入工具目录，不是只挑了几个常用接口
- **代码生成**：AI 可按调用场景生成示例代码（认证、请求体、错误处理），直接拿去用
- **受控边界**：只读直连；写入生成待确认动作；高危二次确认并记审计
- **权限边界**：沿用 JWT 与租户隔离，不绕过平台权限

## 15 演示 A：导入物模型并生成

*约 40 秒*　**演示**

### 人工导入物模型，AI 校验并生成可用产品

1. 人工导入现有物模型文件（厂商提供或腾讯格式）
2. 平台自动识别格式并归一化为标准 TSL
3. AI 校验：结构、业务逐条给出问题与修正建议
4. 人工确认修正后保存，状态直接为已发布
5. 产品配置、产品资产、产品规则链自动生成

- **要看的过程**：导入一份带类型错误的物模型，AI 指出字段与期望类型，修正后校验转绿
- **结论**：导入是人工动作，校验与生成由 AI 与平台接手，人只做确认

## 16 演示 B：修改物模型，增加字段

*约 40 秒*　**演示**

### 产品上线后要加一个字段，从提出到生效要几步

1. 打开已发布产品的物模型，提出新增字段（例：新增"油耗"属性，单位 L，范围 0–500）
2. AI 校验新版本：字段命名、类型、范围、单位、与既有字段的冲突逐项检查
3. 人工确认后保存，生成新的 TSL 版本并发布
4. 平台同步更新产品配置、产品资产与规则链校验规则
5. 设备按新字段上报：平台校验通过、数据落库；旧字段不受影响

- **要看的过程**：故意写一个不合规的字段（如类型与取值冲突），AI 指出问题后再改对
- **结论**：改模型不用停机重建，发布即生效，历史数据语义不中断

# 第五部分　融合终端与更多物联网设备都可无缝接入

## 18 五类设备，一条接入主线

*约 40 秒*

### 从工业网关到低功耗传感器，都能接进同一个平台

| 设备类型 | 典型场景 | 接入方式 | 平台侧统一 |
| --- | --- | --- | --- |
| 工业协议设备 | PLC、DCS、数控、工程机械 | 平台直接对接 OPC-UA / S7 / CAN | 统一物模型 + 规则链校验 |
| 融合终端 | 多协议聚合、边缘采集 | 终端直连，无中转服务 | 子设备按标准设备对象纳管 |
| 直连设备 | 智能表计、车载终端、自研硬件 | 标准 MQTT 直连 | 同一套主题与认证 |
| 低功耗设备 | 传感器、电池供电节点 | 轻量上报，平台侧统一校验 | 设备端不做校验逻辑 |
| 存量设备 | 腾讯云 IoT 存量终端 | 原协议上报，平台归一化 | 迁移不改设备端 |

- **一条主线**：设备形态不同，接入路径不同，但都落到"设备 + 物模型 + 规则链"这一套
- **不挑设备**：工业总线、无线终端、低功耗节点、存量终端都能覆盖
- **不重复建设**：平台侧只有一套模型、一套校验、一套数据链路

**一句话**：设备可以五花八门，平台只需要一套接入逻辑。

## 19 工业协议：平台直接对接

*约 40 秒*

### 工业协议由平台直接对接，融合终端作为边缘接入件

> **强调**：物联网平台可直接对接 OPC-UA / S7 / CAN 等工业协议，现场设备不必先接一套第三方采集或转换系统。

- **对接主体是平台**：工业协议接入能力属于平台，融合终端作为平台的边缘接入组件随平台交付
- **直接读取**：OPC-UA 按节点读、S7 直接读 DB 块、CAN 解析短帧，采集在边缘完成
- **对外统一**：协议差异在边缘消化，对上统一走平台标准接入，平台侧只看到"设备 + 物模型"
- **可持续扩展**：协议以连接器方式接入，新增协议扩展连接器即可，不改平台架构

| 协议 | 典型对象 | 接入方式 |
| --- | --- | --- |
| OPC-UA | PLC、DCS、产线控制 | 按节点读取，结构化工艺参数 |
| S7 | 西门子系列设备 | 直接读 DB 块，存量产线低成本改造 |
| CAN | 车载、工程机械、控制器 | 解析高频短帧运行数据 |
| 后续扩展 | Modbus 等更多工业协议 | 以连接器方式接入，按需扩展 |

**可验证**：平台侧融合终端管理页、各协议连接器状态与采集点、子设备上线记录。

**一句话**：工业协议这一层，平台自己就能接，不依赖外部中间件。

## 20 统一物模型：一份模型，贯穿所有设备

*约 40 秒*

### 不管走终端还是直连，都用同一份 TSL

> **强调**：统一物模型——终端只做点位到字段的映射，子设备沿用产品物模型。

- **同一份 TSL**：子设备的属性、事件、行为沿用产品物模型定义，同型号换终端不重建模型
- **同一套校验**：终端上报同样过产品规则链，类型、范围、枚举、必填一项不少
- **同一条链路**：与直连设备走同一 Kafka 主题、写入同一个时序数据库
- **横向复用**：同一产品在多个工点、多台终端上共用一份模型，新增工点只加终端实例
- **纵向无感**：规则、告警、看板、API 全部按统一模型工作

**可验证**：产品物模型页、子设备的属性映射表、规则链校验结果。

**一句话**：一份模型管到底，平台不需要知道数据是怎么接进来的。

## 21 单跳直连：终端直连平台

*约 40 秒*

### 融合终端直连物联网平台，链路上没有中转服务

> **强调**：终端直连平台上报数据，无需部署额外的中转服务或消息中间队列。

- **直连方式**：终端 MQTT 客户端直连平台网关模式，平台原生支持网关主题与子设备包含关系
- **链路形态**：设备 → 融合终端 → 平台，三段到顶，中间没有第四层
- **现场收益**：少一台机器、少一个要盯的服务、少跨一个系统排障

| 对比项 | 传统"网关 + 中转服务" | 融合终端直连 |
| --- | --- | --- |
| 部署单元 | 网关 + 中转 + 队列 | **仅终端** |
| 故障点 | 多一层，跨系统排障 | **单跳** |
| 子设备建模 | 中转侧再维护一套映射 | **平台侧标准物模型** |
| 扩容 | 中转层跟着扩 | **边缘加终端即可** |

**可验证**：网关连接日志、平台侧网关主题消息、子设备上线记录。

**一句话**：少一层，就少一个深夜被叫起来排障的理由。

## 22 多语言 MQTT：标准协议，生态现成

*约 40 秒*

### 平台走标准 MQTT，各语言用成熟客户端库即可接入

> **强调**：上报数据使用标准 MQTT 协议，不绑定私有 SDK；各主流语言都有成熟客户端库可直接对接。

| 语言 / 场景 | 推荐客户端库 | 说明 |
| --- | --- | --- |
| 跨语言基础 | Eclipse Paho | 官方与社区覆盖 Java、Python、JS、Go、C/C++、Rust、C#、Android、Embedded |
| Python | paho-mqtt / gmqtt | 官方客户端；异步场景可用 gmqtt |
| Java | Paho Java / Android Service | 同步与异步 API；Android 端管理后台服务生命周期 |
| Go | paho.mqtt.golang | 官方 Go 实现，贴近 Go 生态 |
| JavaScript | MQTT.js / Paho JS | Node.js 与浏览器均可用 |
| C / C++ | Paho C / Paho C++ / wolfMQTT | 嵌入式与高性能场景；wolfMQTT 体积小、支持 TLS 1.3 |
| Rust | rumqttc | 纯 Rust、Tokio 异步运行时 |

- **协议能力**：平台支持 MQTT 3.1.1，兼容 5.0；具体到某个库的 5.0 支持需按版本确认
- **对接简单**：连地址与端口 → 用设备令牌认证 → 按物模型字段上报，四步完成
- **无需私有 SDK**：不引入平台自定义封装，避免版本锁定与升级耦合

**可验证**：平台 MQTT 接入地址与认证方式、任意语言客户端的一次上报、平台侧校验记录。

**一句话**：协议是标准的，工具是现成的，对接不用等我们发 SDK。

# 第六部分　腾讯云 IoT 兼容与拓展

## 23 物模型归一化

*约 40 秒*

### 腾讯侧物模型，可以直接导入

- **按腾讯 TSL 规范归一化**：属性、事件、行为映射到平台标准 TSL
- **保留完整语义**：类型、范围、单位、枚举、结构体层级
- **自动识别来源**：依据腾讯格式的 define 特征判断，无需人工声明
- **同一入口**：标准 TSL 与腾讯格式共用导入入口，不会导错
- **设备端零改动**：设备继续按原 MQTT 主题与报文格式上报，迁移只换平台

**需要显式确认**：字符串型 min/max 等源数据元信息，默认按规范丢弃，需要保留时用参数开启，不改语义。

## 24 时序数据灵活加工与下游对接

*约 40 秒*

### 时序数据可编程处理，结果按需对接下游

- **直接操作时序库**：按业务需要编写代码直接查询、加工时序数据，不受固定报表模板限制
- **灵活计算**：聚合、窗口、关联、补点等逻辑可随时调整，改代码即可，不用等产品版本
- **下游对接方式**：结果可通过消息队列、API 接口、直接写入业务数据库等方式交付
- **数据链路闭环**：原始数据留存平台，加工结果按需分发，上游改动不影响下游

| 下游对接方式 | 适用场景 | 特点 |
| --- | --- | --- |
| 消息队列 | 下游系统异步消费、多系统广播 | 解耦、可缓冲、易扩展 |
| API 接口 | 业务系统按需查询、前端展示 | 实时、按权限控制 |
| 直接写入业务库 | 报表、台账、历史归档 | 落地稳定，便于二次分析 |

**可验证**：时序库查询与加工脚本、一条加工结果通过三种方式之一对接下游的记录。

**一句话**：数据怎么用、给谁用、用什么方式给，都按业务需要来。
