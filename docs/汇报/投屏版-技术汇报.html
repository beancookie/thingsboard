单集群已验证 3 万台设备接入

03 AI 辅助

三个场景，一条原则

AI 只提建议，平台负责校验与执行。

A生成与校验物模型

自然语言描述设备 → TSL 草案 → 平台三道校验 → 保存即生效。

B定位数据链路问题

凭证 → 产品 → 规则链 → 主题 → 时序库，逐段排查并指出断点。

C调用平台 OpenAPI

搜索并调用平台接口，可扩展为运维问答入口；写操作必须确认。

CONTROL受控边界

  • 只读直连，写入生成待确认动作
  • 高危操作二次确认并记审计
  • 沿用 JWT 与租户隔离，不绕权限

LIMIT表述边界

生成的是草案，必须过平台校验才落库；"AI 直接改生产数据"这种说法不成立，今天也不讲。

03 AI 辅助

对话即操作，写入必须人点头

READ读操作直接执行

查租户、查产品、查设备、查告警、查网关列表；返回结构化结果，不产生待确认动作。

WRITE写操作必须确认

动作名、参数、风险等级一并展示；确认后才调用平台 REST；高危二次确认并记审计。

接口目录可扩展

权限不绕过

复杂动作有 handler

04 融合终端无缝接入

无需中转服务：网关直连平台

去掉中间那一段，少一个故障点、少一套运维。

×网关 + 中转服务

  • 网关 → 中转 → 平台，多一跳
  • 中转层要单独部署、监控、扩容
  • 排障需跨系统，先查中转

✓融合网关直连

  • 网关 MQTT 直连平台网关模式
  • 平台原生支持网关主题与子设备关系
  • 没有中转服务这一层
对比项网关 + 中转融合网关直连
部署单元网关 + 中转 + 队列仅网关
故障点多一层，跨系统排障单跳
子设备建模中转侧再维护一套映射平台侧标准物模型

04 融合终端无缝接入

网关与子设备共用一套标准物模型

不是"网关一套格式、平台一套格式"，而是同一份 TSL、同一套校验。

同一份 TSL

子设备沿用产品物模型，网关只做点位到字段的映射；同型号换网关，模型不重建。

同一套校验

网关上报同样过产品规则链：类型、范围、枚举、必填，一项不少。

同一条链路

与直连设备走同一 Kafka 主题、同一入湖逻辑，下游无需区分接入方式。

横向：多网关复用

同一产品在多个工点、多台网关上复用同一模型，新增工点只加网关实例。

纵向：平台无感

规则、告警、看板、API 全部按统一模型工作，不为网关单开分支。

04 融合终端无缝接入

三步完成融合终端接入

建议用实物网关或现场录屏，比模拟器更有说服力。

  1. 网关以网关模式上线：在线状态与连接时间刷新
  2. 子设备注册并上线，建立 Contains 关系：网关设备页签可见
  3. 三类协议数据上报：同一产品下三个子设备均有数据点
  4. 平台下发 RPC，网关转发：设备回执、状态变化

要看懂这件事

子设备在平台里是标准设备对象：有属性、有关系、有在线状态，能被检索、授权、规则引用。

反面案例：只把一包数据透传上来，平台无法对子设备做治理——那不叫接入。

预期结果子设备与直连设备无差别进入规则链与时序库
兜底无实物网关时播放 2 分钟接入录屏，或本地模拟脚本复现

05 腾讯云 IoT 兼容

腾讯侧物模型，可以直接导入

导入即识别、即归一化、即校验，客户不需要先"翻译"一遍。

  • 按腾讯 TSL 规范归一化
    属性 / 事件 / 行为映射到标准 TSL，类型、范围、单位、枚举、结构体层级保留
  • 自动识别来源
    依据腾讯格式的 define 特征判断，不要求操作员先声明
  • 标准与兼容格式同一入口
    不会导错，也不需要维护两套导入流程

保留

数据类型、取值范围、枚举映射、单位、读写模式、事件参数、结构体字段层级。

需显式确认

字符串型 min/max 这类源数据元信息，默认按规范丢弃；需要保留时用参数开启，不偷偷改语义。
