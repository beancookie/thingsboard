- 平台租户管理员
- 设备接入和运维人员
- 需要实现跨设备自动控制的第三方接入方
- 负责场景联调、排障和交付的人员

- 设备已绑定产品配置。
- 设备关系已建立，或已确定目标设备名称。
- 执行设备在线并支持 RPC 或约定的 MQTT 主题。
- 已了解规则引擎的基本操作，见 [规则引擎使用手册](规则引擎使用手册.md)。

## 2. 场景联动是什么

场景联动是指：一个设备的状态变化，经过条件判断后，自动控制另一个或多个设备。

一个完整场景包含：

| 组成 | 说明 |
| --- | --- |
| 触发 | 设备遥测、属性、事件、告警或在线状态 |
| 条件 | 阈值、持续时间、多个设备数据组合 |
| 目标 | 要控制的设备 |
| 动作 | RPC、MQTT 消息、REST API、告警或通知 |
| 状态 | 场景当前是否已执行、是否已恢复 |
| 失败处理 | 目标离线、RPC 超时、执行失败时的告警或通知 |

平台没有独立的「场景」实体，场景联动由规则链、设备关系和设备能力组合实现。

### 2.1 核心思路

```text
触发设备上报
  -> 规则链判断条件
  -> 切换到目标设备
  -> 生成控制指令
  -> RPC / MQTT / REST API
  -> 成功或失败分支
  -> 记录结果、告警或通知
```

### 2.2 三种常见实现方式

| 方式 | 适用场景 |
| --- | --- |
| RPC | 目标设备支持平台 RPC，推荐使用 |
| MQTT | 目标设备只订阅自定义主题，不支持平台 RPC |
| REST API | 目标设备或外部系统提供 HTTP 接口 |

### 2.3 关键限制

- RPC 节点默认发给消息的来源设备，不是任意设备。
- 要控制另一个设备，必须先切换消息来源。
- 目标设备必须在线，否则 RPC 会失败或超时。
- 规则引擎单条消息是无状态的，场景状态需要额外保存。
- 跨租户设备不能直接联动。

## 3. 设计一个场景

### 3.1 明确触发设备和执行设备

先列出：

- 哪个设备产生触发数据
- 触发数据是什么字段
- 满足什么条件
- 要控制哪个设备
- 控制方法是什么
- 失败时通知谁

示例：

```text
触发设备：motion-01
触发字段：motion
触发条件：motion = true
执行设备：light-01
执行方法：RPC setState
执行参数：{"state":"ON"}
失败处理：创建告警并发送通知
```

### 3.2 设计设备关系

推荐在设备之间建立明确的关系，例如：

```text
motion-01 --Controls--> light-01
temperature-01 --Controls--> air-conditioner-01
```

关系类型可以自定义，但建议语义清晰：

| 关系类型 | 说明 |
| --- | --- |
| `Controls` | 控制关系 |
| `ConnectedTo` | 连接关系 |
| `Contains` | 包含关系 |
| `Manages` | 管理关系 |

在设备详情「关系」页签中添加关系。

> 截图占位：`images/scenes/02-device-relations.png`

### 3.3 选择目标设备发现方式

| 方式 | 说明 | 适用场景 |
| --- | --- | --- |
| 关联实体 | 按关系查找目标设备 | 推荐，设备多时更灵活 |
| 名称模板 | 按设备名称查找 | 目标设备固定、数量少 |
| 固定设备 | 在节点中写死设备名称 | 简单测试 |

关系方向要和配置一致：

- 如果关系是 `motion-01 --Controls--> light-01`，使用 `FROM`。
- 如果关系是 `light-01 --ControlledBy--> motion-01`，使用 `TO`。

### 3.4 设计成功和失败分支

每个场景至少设计两个分支：

```text
成功 -> 记录日志 / 保存执行结果
失败 -> 创建告警 / 发送通知 / 稍后重试
```

常见失败原因：

- 目标设备离线
- RPC 超时
- 目标设备未实现方法
- 关系不存在
- 设备名称变更
- 网络异常

### 3.5 设计防重复和防循环

- 使用 `deduplication` 节点对重复消息去重。
- 使用设备或资产属性保存「场景已执行」状态。
- 避免 A 控制 B、B 又控制 A。
- 对频繁上报的设备设置合理的时间窗口。
- 对执行结果做幂等处理，重复指令不应产生副作用。

### 3.6 设计场景状态

规则引擎消息默认无状态。建议把场景状态保存在：

- 设备服务端属性
- 资产服务端属性
- 告警
- 独立状态设备或实体

示例状态属性：

```text
scene_living_room_light = ON
scene_living_room_last_exec_ts = 1760000000000
```

## 4. 准备设备与关系

### 4.1 确认设备

1. 进入「设备」页面。
2. 确认触发设备和执行设备存在。
3. 确认设备已绑定产品配置。
4. 确认执行设备在线。

### 4.2 建立关系

1. 打开触发设备详情。
2. 进入「关系」页签。
3. 点击「添加」。
4. 填写关系类型，例如 `Controls`。
5. 选择方向和目标设备。
6. 保存关系。

### 4.3 确认目标设备支持 RPC

MQTT 设备通常需要：

- 订阅 `v1/devices/me/rpc/request/+`
- 收到请求后执行动作
- 发布 `v1/devices/me/rpc/response/{requestId}`

请求示例：

```json
{
  "method": "setState",
  "params": {
    "state": "ON"
  }
}
```

> 截图占位：`images/scenes/11-rpc-topics.png`

### 4.4 确认设备名称

如果使用名称模板查找目标设备，设备名称必须稳定，不要随意修改。

## 5. 创建场景规则链

### 5.1 创建独立规则链

1. 进入「规则引擎」。
2. 点击「创建新规则引擎」。
3. 名称填写场景名称，例如 `客厅有人开灯`。
4. 可选开启调试模式。
5. 保存。
6. 进入规则链编辑器。

> 截图占位：`images/scenes/03-create-scene-rulechain.png`

建议为每个场景创建独立规则链，不要直接修改产品共用规则链。

### 5.2 绑定规则链

可以按以下方式让场景规则链接收消息：

| 方式 | 说明 |
| --- | --- |
| 绑定产品配置 | 特定类型设备的消息进入场景规则链 |
| 根规则链 | 所有未绑定其他规则链的消息进入 |
| 嵌套规则链 | 由产品规则链通过规则链节点调用 |

生产环境推荐使用独立场景规则链，并通过嵌套规则链或产品配置绑定。

### 5.3 常用节点

| 节点 | 用途 |
| --- | --- |
| `message type switch` | 只处理遥测或指定消息类型 |
| `script` | 读取字段、判断条件、生成 RPC 参数 |
| `filter` | 条件不满足时丢弃消息 |
| `switch` | 多条件分支 |
| `related entity data` | 读取关联设备数据 |
| `originator telemetry` | 读取当前设备最新遥测 |
| `change originator` | 切换消息来源到目标设备 |
| `rpc call request` | 向目标设备发送 RPC |
| `mqtt` | 发布自定义 MQTT 消息 |
| `rest api call` | 调用外部 HTTP 接口 |
| `deduplication` | 防重复触发 |
| `create alarm` | 失败时创建告警 |
| `notification` | 发送通知 |

## 6. 示例一：人体感应开灯

### 6.1 设备与关系

| 设备 | 作用 |
| --- | --- |
| `motion-01` | 人体感应，上报 `{"motion": true}` |
| `light-01` | 灯，支持 RPC 方法 `setState` |

关系：

```text
motion-01 --Controls--> light-01
```

### 6.2 规则链

```text
motion-01 遥测
  -> message type switch（Post telemetry）
  -> script（读取 motion）
  -> filter（motion === true）
  -> change originator
       source: Related Entity
       relation: Controls
       direction: FROM
  -> script
       payload:
       {
         "method": "setState",
         "params": { "state": "ON" }
       }
  -> rpc call request（timeout 10s）
       Success -> log / save time series
       Failure -> create alarm / send notification
```

> 截图占位：`images/scenes/04-scene-trigger-filter.png`
>
> 截图占位：`images/scenes/05-change-originator.png`
>
> 截图占位：`images/scenes/06-rpc-config.png`

### 6.3 关键配置

**change originator**

- 来源：关联实体
- 关系类型：`Controls`
- 方向：`FROM`
- 最多层级：1

**rpc call request**

- 超时：10 秒
- 消息体必须包含 `method` 和 `params`
- 成功分支记录结果
- 失败分支创建告警或发送通知

> 截图占位：`images/scenes/07-scene-success-failure.png`

### 6.4 验证

1. 确认 `light-01` 在线。
2. 确认 `light-01` 已订阅 RPC 主题。
3. 模拟 `motion-01` 上报 `motion=true`。
4. 查看 `light-01` 是否收到 RPC 请求。
5. 查看规则链成功分支是否执行。
6. 关闭 `light-01` 再测试，确认失败分支生效。

## 7. 示例二：有人且光照低才开灯

### 7.1 设备与关系

| 设备 | 作用 |
| --- | --- |
| `motion-01` | 人体感应 |
| `light-sensor-01` | 光照传感器，上报 `illuminance` |
| `light-01` | 灯，支持 RPC |

### 7.2 规则链

```text
motion-01 遥测 motion=true
  -> change originator 到 light-sensor-01
  -> originator telemetry 读取 illuminance
  -> change originator 到 light-01
  -> script 判断 metadata.illuminance < 100
  -> script 生成 method/params
  -> rpc call request
```

> 截图占位：`images/scenes/08-multi-condition.png`

### 7.3 读取其他设备数据的两种方式

| 方式 | 说明 |
| --- | --- |
| `related entity data` | 通过关系读取关联设备的属性或最新遥测 |
| `change originator` + `originator telemetry` | 先切换到目标数据设备，再读取遥测 |

如果设备之间没有直接关系，可以使用设备名称模板切换消息来源。

### 7.4 条件组合建议

- 把条件写在 `script` 或 `filter` 节点中。
- 条件不满足时走 `False` 或 `Failure` 分支。
- 多个条件建议加注释，说明业务含义。
- 阈值建议保存在设备或资产属性中，避免写死在脚本里。

## 8. 示例三：温度超限联动空调并告警

### 8.1 场景

```text
temperature-01 温度 > 30
  -> 开启 air-conditioner-01
  -> 创建高温告警
  -> 发送通知

temperature-01 温度 <= 30
  -> 关闭 air-conditioner-01
  -> 清除高温告警
```

### 8.2 规则链

```text
temperature-01 遥测
  -> message type switch
  -> script（读取 temperature）
  -> switch
       high -> change originator 到 air-conditioner-01
               -> script（setMode COOL）
               -> rpc call request
               -> create alarm
               -> notification
       normal -> change originator 到 air-conditioner-01
                 -> script（setMode OFF）
                 -> rpc call request
                 -> clear alarm
```

> 截图占位：`images/scenes/13-alarm-notification.png`

### 8.3 注意

- 告警类型和通知模板要提前创建。
- 告警级别建议使用「主要」或「严重」。
- 清除告警条件要和创建条件对应。
- 通知规则可以按告警级别过滤。

告警和通知配置见 [告警与通知使用手册](告警与通知使用手册.md)。

## 9. 无 RPC 设备的联动

### 9.1 使用 MQTT 节点

目标设备只订阅自定义主题时：

```text
触发设备遥测
  -> 条件判断
  -> script 生成自定义 JSON
  -> mqtt 节点
       目标消息代理 或主题
       例如：scene/light/control
```

目标设备订阅：

```text
scene/light/control
```

消息示例：

```json
{
  "device": "light-01",
  "action": "ON",
  "source": "motion-01",
  "ts": 1760000000000
}
```

> 截图占位：`images/scenes/12-mqtt-fallback.png`

### 9.2 使用 REST API

```text
触发设备遥测
  -> 条件判断
  -> script 生成请求体
  -> rest api call
       POST https://example.com/api/scene/control
```

### 9.3 使用 Kafka 或外部场景引擎

复杂场景可以把规则引擎作为触发器，把消息发送到 Kafka，由外部场景引擎统一编排。

## 10. 防重复、防循环和状态管理

### 10.1 防重复

- 使用 `deduplication` 节点。
- 在消息元数据中保存上次执行时间。
- 在设备或资产属性中保存场景状态。
- 只在状态变化时执行控制。

### 10.2 防循环

```text
A 控制 B
B 状态变化又控制 A
A 再次控制 B
```

避免方法：

- 控制指令不要再次触发同一场景。
- 使用独立控制主题或 RPC 方法。
- 在脚本中判断来源和当前状态。
- 对控制消息设置标记，例如 `metadata.sceneCommand=true`。

### 10.3 离线处理

- RPC 失败时进入失败分支。
- 目标设备离线时创建告警或发送通知。
- 可配置稍后重试，但要有最大重试次数。
- 不要无限重试。

### 10.4 记录执行结果

建议记录：

- 场景名称
- 触发设备
- 目标设备
- 执行动作
- 执行时间
- 成功或失败
- 失败原因

## 11. 调试与验证

### 11.1 开启规则链调试

1. 打开场景规则链。
2. 开启调试模式。
3. 保存规则链。
4. 在「事件」页签查看调试事件。
5. 调试完成后关闭调试。

> 截图占位：`images/scenes/10-rulechain-debug.png`

### 11.2 验证步骤

1. 确认触发设备在线。
2. 确认目标设备在线。
3. 确认设备关系存在。
4. 模拟触发设备上报。
5. 查看规则链消息是否进入。
6. 查看 `change originator` 后的消息来源。
7. 查看目标设备是否收到 RPC 或 MQTT 消息。
8. 查看成功和失败分支。
9. 查看告警和通知是否发送。

### 11.3 常用排查点

- 消息类型是否匹配。
- 过滤条件是否过严。
- 设备关系方向是否正确。
- 目标设备名称是否变化。
- RPC 方法名和参数是否正确。
- 目标设备是否订阅正确主题。
- RPC 超时是否过短。
- 规则链是否已保存并绑定。

## 12. 权限、安全与最佳实践

- 场景规则链只由租户管理员维护。
- 只允许控制白名单内的设备。
- 不要跨租户控制设备。
- 重要控制动作要记录审计信息。
- 对高频触发设置速率限制和防抖。
- 生产环境关闭规则链调试。
- 失败分支必须配置告警或通知。
- 场景规则链命名要清晰，例如「区域-触发-动作」。
- 修改场景前先备份或导出规则链。
- 上线前在测试设备上完整验证。

## 13. 常见问题

| 问题 | 排查 |
| --- | --- |
| 场景没有触发 | 检查规则链绑定、消息类型、过滤条件和设备是否在线 |
| 目标设备没有收到 RPC | 检查是否先执行 `change originator`，目标设备是否在线 |
| RPC 超时 | 检查目标设备 RPC 主题、网络、超时时间和设备响应 |
| 目标设备收到错误方法 | 检查 `method` 和 `params` 是否符合设备协议 |
| 关系查找失败 | 检查关系类型、方向和目标设备 |
| 设备名称模板找不到设备 | 检查设备名称是否变化，名称是否在当前租户 |
| 场景重复执行 | 增加 `deduplication`、状态判断或时间窗口 |
| 场景循环触发 | 检查控制消息是否再次进入同一场景，增加来源和状态判断 |
| 目标设备离线 | 配置失败分支，创建告警或通知 |
| 客户用户看不到执行结果 | 检查设备、告警是否分配给客户或设为公开 |
| 跨租户设备无法控制 | 平台不支持跨租户联动 |
| 无 RPC 设备无法联动 | 改用 MQTT 节点、REST API 或外部场景引擎 |
| 调试看不到消息 | 检查调试模式、节点调试设置和调试有效期 |
